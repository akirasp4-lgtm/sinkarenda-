# 社長予定をCloudflare(D1)から読む — 設計書

作成: 2026-08-26
状態: 利用者承認済み（「うん、それでいいよ」2026-08-26）

## 1. なぜやるか

同じ測り方で本番を3回ずつ測った結果、読み取り速度に約15倍の差がある。

| | 読みに行く先 | 実測 |
|---|---|---|
| 社員用 index.html / admin.html | Cloudflare | 0.12 / 0.35 / 0.15 秒 |
| 社長用 president.html | GAS | 4.14 / 2.65 / 2.68 秒 |

開いた瞬間の表示（キャッシュ描画 148ms vs 172ms）と保存の体感（楽観的保存）は
2026-08-26 の作業で既に同等になっている。**残っているのは「裏で最新を取ってくる速さ」だけ。**
両画面とも「最新が届くまで保存させない」安全装置を持つため、この差はそのまま
**「開いてから登録できるようになるまでの待ち時間」**として社長に見えている（約3秒）。

## 3. 方針

**社員用と同じ形をもう一組つくる。社員用のコードは1行も変えない。**

```
GAS（社長予定シート）
  ↓ Cronが5分ごとに pres_list を叩いて取り込む
D1: pres_snapshot（1行に丸ごと）
  ↓ /api/president（PIN照合）
president.html が読む（失敗したら自動でGASへ戻る）

書き込み（追加・修正・削除）は今までどおり GAS へ直接。D1は読み取り専用の写し。
```

## 4. 決めたこと

### 4.1 記録表は社員用と分ける（最重要）

社員用の鮮度判定 `read.js:getLastSuccessAt` は `sync_log` の **ok=1 の直近1件**を見る。
ここに社長予定の同期結果を混ぜると、**社員用の同期が失敗し続けていても社長予定の同期成功で
「新しい」と誤判定**され、社員に古いデータを正常として返す。`index.js:isSyncRateLimited`
（直近1分の行数でレート制限）も同様に歪む。

→ **`pres_sync_log` を別テーブルとして作る。** `sync_log` には一切書かない。

同じ理由で snapshot も別テーブル `pres_snapshot` にする（`snapshot` は `CHECK (id = 1)` で
1行しか持てず、そもそも相乗りできない）。

### 4.2 スキーマの適用方法

`cf/schema.sql` は先頭で `DROP TABLE IF EXISTS snapshot / sync_lock / sync_log` を行う破壊的な作り。
本番切替後（現在）にこれを再適用すると社員用のD1が一瞬空になる。

→ **`cf/schema-president.sql` を新規に作り、追加分だけを流す。** `cf/schema.sql` には
「社長予定は schema-president.sql 側にある」旨の追記のみ行い、**再適用はしない**。

### 4.3 ロックは作らない（意図的な簡略化）

社員用は `sync_lock` を持つが、コード自身のコメントが
「ロックはbest-effortに過ぎず、正しさの最終防衛は `fetch_started_at` のWHERE条件が担う」
と明言している。社長予定は件数が2桁と小さく取得も速いため、**世代ガード（条件付き単一文の
書き込み）だけを実装し、ロックテーブルは作らない**。守りの本体は同じものが入る。

### 4.4 PINの置き場

Cronが `pres_list` を呼ぶためにPINが要る。`cf/wrangler.toml` は**公開リポジトリに入る**ため
そこには書かない。

→ **Cloudflareのシークレット `PRES_PIN`**（`npx wrangler secret put PRES_PIN`）。
未設定なら `syncPresident` は「PIN未設定」として失敗を記録し、**何も壊さず**終わる
（`/api/president` も鮮度ガードで error を返し、画面は自動でGASへ落ちる＝今と同じ速度に戻るだけ）。

### 4.5 `/api/president` は POST

PINをURLのクエリに載せない（アクセスログ・Referer・履歴に残るため）。
`POST /api/president` に `{"pin":"...."}` をJSONで送る。

- PIN不一致 → `{status:'error', message:'認証に失敗しました'}` を **403** で返す。
  文言はGAS（`gas.js:205`）と揃える（画面側の分岐を増やさないため）。
- **PIN試行のレート制限**を入れる（`pres_sync_log` ではなく、失敗回数を数える軽い仕組み）。
  社長の操作は何も変わらない。正しいPINを入れる限り一度も当たらない。
- Origin検証は**しない**。社長用はホーム画面PWAからの利用があり、Originが
  `https://akirasp4-lgtm.github.io` にならない経路が有りうるため、締め出す危険の方が大きい。

### 4.6 書いた直後に古い写しを読まない

社員用と同じ二段構え。

1. 追加・修正・削除の**成功後に `/api/pres-sync` をPOST**して即座に取り込ませる
2. **その同期の「確実な成功」を観測するまではGASを優先**する（時間経過では絶対に解除しない）

社員用の `sync-guard.js` にある `createPreferGasTracker` の考え方をそのまま使う。
`sync-guard.js` 自体は社員用が読み込んでおり、**社長用も同じファイルを読み込んで同じ関数を使う**
（ファイルは変更しない＝社員用の挙動に影響しない）。

### 4.7 取り込みの守り

社員用から持ち込むもの:

| 守り | 内容 |
|---|---|
| 応答検証 | `status==='ok'` かつ `rows` が配列であること。違えば書き込まず失敗を記録 |
| サイズ上限 | 1,500,000バイト超なら中止（D1の1行上限に対する余裕） |
| 世代ガード | 保存済みより古い `fetch_started_at` の結果では上書きしない（条件付き単一文） |
| 急減ガード | 件数が保存済みの半分未満なら拒否。**同じ内容の拒否が30分続いたら受け入れる**（正当な一括削除で永久に詰まらないように） |
| 変更なしスキップ | ハッシュ一致なら書き込まない。ただし `ok=1` で記録する（鮮度ガードを誤発火させないため） |
| 鮮度ガード | 直近の成功が15分より古ければ `/api/president` は error を返す（→ 画面はGASへ） |

社員用にある「マスタの急減チェック」は社長予定にマスタが無いので対象外。
`force=1` の脱出口と、その専用クールダウンも今回は作らない（急減ガードに30分の
自己回復があるため、詰まったままにはならない）。
