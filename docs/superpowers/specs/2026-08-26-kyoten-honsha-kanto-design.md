## 1. 依頼の核心

> **会社名で分けるのではなく、「本社／関東支店」という管理区分を別で持たせること。**

打合せメモは「関東と大阪のカレンダーを1本に」だったが、依頼書はもう一段深い。
**法人（グローライズ／GRミツマ）と拠点（本社／関東支店）を別の軸にする。**
GRミツマを関東支店として運用していても、将来GRミツマ法人で本社案件を持つことは
ありうるため、片方から他方を導出してはいけない。

## 3. 決めたこと

### 3.1 拠点は「予定1件ごと」に持つ（20列目）

`HEADERS` に **`拠点`** を追加して20列にする。値は3つ:

| 値 | 意味 |
|---|---|
| `本社` | 本社の予定 |
| `関東支店` | 関東支店の予定 |
| `両方` | 本社・関東の両方に関係する予定（③。1件だけ登録して両方の画面に出る） |

**なぜ人（職人マスタ）に持たせないか**: 「グローライズの人が関東案件へ応援に行く」を
表現できない。依頼書は売上を拠点別に見たいと言っており、それは案件の属性であって
人の属性ではない。

**なぜ会社から導出しないか**: 依頼書が明示的に禁じている。導出だと
「GRミツマ法人で本社案件」を永久に表現できず、あとから直せない。

### 3.2 入力は増やさない ─ 現場（案件）から自動で入る

現場マスタに **`拠点`** 列（11列目）を追加する。

```
予定を登録する
  → 現場名を選ぶ
    → その現場の拠点が自動で入る（現場マスタに登録済みなら）
    → 未登録なら、会社から既定値を入れる（GRミツマ→関東支店／他→本社）
  → 違うときだけ、その場で変えられる
```

**重要**: 会社からの自動判定は**既定値を入れるためだけ**に使い、
決まった値は**行ごとに実際に保存する**。読むときに会社から計算し直さない。
これで「会社名で分けない」という依頼書の要件を満たしつつ、日々の入力は増えない。

### 3.3 画面は3ビュー切替（②）

既存の会社切替とは**別のプルダウン**として「拠点」を置く。

| 選択 | 出るもの |
|---|---|
| 全社 | 全部。**どちらの予定か一目で分かるようにする**（予定カードに拠点の印を付ける） |
| 本社 | 拠点が `本社` または `両方` の予定 |
| 関東支店 | 拠点が `関東支店` または `両方` の予定 |

`両方` が両側に出ることで③（二重登録の廃止）が成立する。

### 3.4 過去データ（利用者承認済み・2026-08-26）

既存2,625行を**会社から一括で埋める**。GRミツマの85行→`関東支店`、他→`本社`。
これまでの運用実態と一致する。違う行はあとから個別に直せる。
**実行前にバックアップを取る**（`_local/backup_YYYYMMDD/`。アーカイブ作業と同じ手順）。

### 3.5 反映の順番（ここを間違えるとデータの取り込みが止まる）

Cloudflare側が19列ちょうどを検査しているため、順番を守る。

1. **Worker を先に出す** — `EXPECTED_HEADERS` の検査を「**先頭19列が一致すれば通す**」に緩める
   （20列目以降は許容）。この時点では挙動は変わらない＝**無影響**。
2. **GAS を出す** — 20列目 `拠点` を書き出すようになる。Workerは1で緩めてあるので取り込みは続く。
3. **過去データを埋める**（3.4）。
4. **画面を出す** — 3ビュー切替が使えるようになる。

**戻し方**: 各段階で独立に戻せる。画面だけ戻す／GASを前バージョンへ／Workerを前へ。
列を足すこと自体は破壊的ではない（既存19列の位置は動かさない）。

  `会社別集計` `月別集計` 等の集計エンジンには手を入れない。
  **理由**: 集計エンジンは1,500行あり、金額機能は2026-06-11の決定で「寝かせる」扱い。
  拠点の軸が実データで安定してから繋ぐ方が安全。

  元請名・現場名・工番・事業部があるため、**何が足りないかを実データで確認してから**にする。
