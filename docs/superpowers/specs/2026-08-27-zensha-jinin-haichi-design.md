## 1. 実データから判明した、設計を左右する事実

2026-08-27 に本番API（`https://yotei-api.miscjigyoubu.workers.dev/api/schedule`）から全2,664行を取得して計測した。

### 1.1 【最重要】「重複」は今のデータでは判定できない

要件3を額面どおり実装すると**狼少年になる**。判定方法ごとの実測ヒット数:

| 判定のしかた | ヒット | 中身 |
|---|---|---|
| 同じ人・同じ日に2件以上 | **250件** | 「現場＋安全会議」「現場＋事務所」など正常が大半 |
| 出勤〜退勤の時間が重なる | **217件** | 出退勤は99%入力済みだが `08:00-17:00` の定型。ほぼ全部重なる |
| 人工の合計が1.0超 | 189件 | 人工は給料の数字。**全行が1**で時間の意味を持たない |
| **同じ日に別々の「現場作業」系** | **47件**（今日以降12件） | ✅ 物理的に不可能。**これだけが本物** |

実例（今日以降・本物）:
```
2026-06-29 河原  きんでん西/SB 若王寺 再々リビジット ＋ きんでん西/アムールみその
2026-07-06 中島  きんでん西/エイペックス上本町 ＋ きんでん西/特別養護老人ホーム南野の庭
2026-07-09 元    ナンジョウ/茨木仕上げ最終日 ＋ ナンジョウ/茨木市エアコン ＋ オリエンス/柏原老人ホーム
```

**採用する判定ルール（フェーズ2で実装）**:
> 同じ人・同じ日に、**作業区分が現場系**（`現場作業` `置局` `着打ち` `撤去品返却`）で
> **元請＋現場名が異なる**行が2件以上ある。ただし昼と夜勤は別枠として数える。
> `夜勤`列が `予定` `休み` の行は対象外。

`事務所` `現調` `移動` `カギ借用` `材料引取・検品` `前乗り` `その他` は
**同じ日に現場と両立する正常な作業**なので警告しない。

### 1.2 資格・経験のデータが存在しない

職人マスタは `氏名／会社／事業部／単価` の**4列だけ**。要件5・要件9の「資格不足」は
**データを作るところから**になる。AIの問題ではない。

### 1.3 マスタが汚れている

| 問題 | 件数 | 影響 |
|---|---|---|
| 職人マスタの氏名重複 | 71行中 実名62人（**9件重複**） | 空き人員・稼働率が水増しされる |
| 予定が0件の登録 | 62人中**14人** | `応援3` `デモ` `管理` など人でない枠。空きリストに出てしまう |
| マスタに無いが予定に出る人 | 1人（`杉本凌（弟）`） | 集計から漏れる |
| 会社名の文字化け | 1行（`グロ?ライズ`） | どのビューにも出ない迷子データ |
| 事業部が空欄 | **60%**（1,595行） | 事業部での絞り込みが機能しない |

### 1.4 編集すると行が作り直され、IDが変わる

`gas.js` の `update` は「新しい行を追加 → 古い行を削除」（`gas.js:600-617`）。
- ✅ 削除直前に古い行の値が `sheet.getDataRange().getValues()` で手元にある → **変更前の記録は容易**
- ⚠️ **IDが変わる** → 履歴は「旧ID→新ID」を繋がないと遡れない

### 1.5 作業区分は4種類ではなく12種類

引き継ぎ書は4種類（現場作業／倉庫／休み／撤去品返却）と記載しているが、実データは12種類。
`その他` が **833件（31%）** と最多。要件2の「工事種別で絞り込む」はこの実態に合わせる。

## 2. 設計の3原則

### 原則1 — 原本はスプレッドシートのまま。列とシートを足すだけ

事務担当が手で直せることが今の運用を支えている。2026-08-26 の拠点追加で
`ensureColumns_` によるヘッダ拡張を3回、無事故で通した。同じ手順を使う。

**却下した案**:
- 案B（Cloudflare D1 を原本に格上げ）: `gas.js` 3,300行の書き直しが必要で、毎日71人が使う本番を長期間不安定にする。
  かつ**事務担当が手で直せなくなる**副作用が実務上致命的。行数が重くなった段階で再検討すればよい。
- 案C（予定はシート・新マスタはD1）: 原本が2箇所に割れ、どちらが正か分からなくなる。

### 原則2 — 「案件ごとに組み替える」運用を殺さない

依頼書に明記: **「GRでは固定班ではなく、案件ごとに人員を組み替える運用」**。
したがって**部隊を人（職人マスタ）に固定で持たせてはいけない**。
拠点と同じく **予定1件ごと** に持たせる。

これにより社長が挙げた「奥田さんの案件で塗装と内装が同時に始まって班が分かれる」
＝**同じ責任者が1部隊と2部隊を同時に持つ**が、そのまま表現できる。

職人マスタの `既定部隊` は**入力の初期値を入れるためだけ**に使い、
決まった値は**行ごとに実際に保存する**（拠点で確立した方式）。

### 原則3 — AIは1か所だけ

| 依頼の書き方 | 実際に必要なもの | 費用 |
|---|---|---|
| 空き人員を**AIが**抽出 | ただの引き算 | 0円 |
| **AI**アラート（重複・不足・空き・翌日現場・未確定・延期） | 決まった計算＋Cron | 0円 |
| 移動時間が現実的でない予定 | **地図が要る。現場マスタに住所の列が無い** | 保留 |
| **AI人員配置提案** | ✅ **ここだけ本物のAI** | Claude API 1回数円 |

家風ルール「確定処理はAIの判断に委ねずコードで固定」（`Claude/CLAUDE.md` §1 🎣）に一致。
計算で出せるものをAIにやらせると、間違えるうえに毎回課金される。

## 3. フェーズ1（土台）— 本書で実装する範囲

### 3.1 日報データ: 20列 → 21列

```
[...既存20列..., '部隊']
```

| 値 | 意味 |
|---|---|
| `1部隊`〜`4部隊` | その予定でその人が属する班 |
| 空欄 | 部隊に属さない（事務所・休み等） |

**入力を増やさない**: 氏名を選ぶと職人マスタの `既定部隊` が自動で入る。違うときだけ変える。

⚠️ 既存20列の位置は**1つも動かさない**（動かすと集計エンジン1,500行が全部壊れる）。

### 3.2 職人マスタ: 4列 → 6列

```
['氏名','会社','事業部','単価','既定部隊','有効']
```

| 追加列 | 用途 |
|---|---|
| `既定部隊` | 入力の初期値。空欄可 |
| `有効` | `○`/`×`。**人でない14件を空き人員リストから外す**（1.3） |

### 3.3 現場マスタ: 11列 → 12列

```
[...既存11列..., 'ステータス']
```

`見積中` `受注` `準備中` `施工中` `残工事` `完工` `延期` `中止`

⚠️ **既存の `完了` 列は残す**（集計が参照）。`完工`・`中止` を選ぶと `完了=TRUE` を自動で立て、
それ以外を選ぶと `完了=FALSE` に戻す。既存の「完了にする」ボタンとの二重管理を避けるため、
**ステータスを正、`完了` を従属**とする。

移行時の初期値: 既存の `完了=TRUE` → `完工`、`完了=FALSE` → `施工中`。

### 3.4 新シート「変更履歴」（8列）

```
['日時','操作','旧ID','新ID','項目','変更前','変更後','実行者']
```

- `add` … 旧IDは空。項目は `(新規)`、変更後に現場名など要約
- `update` … **変わった項目の数だけ行を作る**。旧ID→新IDで追跡可能（1.4）
- `delete` … 新IDは空。全項目を1行に要約して残す

既存の `操作ログ` シートは**そのまま残す**（消さない）。用途が違う（操作ログ＝誰が何をしたか、
変更履歴＝何が何に変わったか）。

**行数の見込み**: 1回の編集で平均3〜5行。現在の運用ペース（更新者31人・3ヶ月で2,664行）から
年間およそ2〜4万行。スプレッドシートの上限（1,000万セル）には十分収まる。
1年経ったらアーカイブする運用にする（既存のアーカイブ機構と同じ形）。

### 3.5 役割の呼称変更 — ★表示だけ変える（保存値は変えない）

社長指示（2026-08-24）は **「代表者」→「責任者」に呼称変更**。
**呼称＝呼び方なので、画面の表示ラベルだけを変える。**

| | 変える | 変えない |
|---|---|---|
| 画面の表示 | `代表者` → **`責任者`** ／ `同行メンバー` → **`班員`** | — |
| スプレッドシートに保存される値 | — | **`代表` / `同行` のまま** |

**なぜ保存値を変えないか（重要）**:
`代表`・`同行` は**データそのもの**で、`=== '代表'` という比較が
**gas.js 5箇所・index.html 38箇所・admin.html 38箇所**に散らばっている。
1箇所でも書き換え漏れると静かに壊れる。特に危険なのは:

- `gas.js:477` `rows.find(r => r.role === '代表')` … 代表者が見つからないと
  **事業部が決まらず工番が空で保存される**
- `gas.js:1219` グループの代表者名の決定
- `gas.js:3054-3058` 工番の一括付与（`backfillJobNos`）

加えて既存2,650行（代表1,284 / 同行1,366）の書き換えも要る。
**得られるものは呼び名だけで、失うリスクが大きすぎる。**

将来どうしても保存値を変えたくなったら、表示層だけの変更なので後から独立してやれる。

**変える箇所（表示ラベルのみ）**: `index.html` / `admin.html` の
`<label>`・`<option>` の文言・`member-label`・カレンダーの `（代表）` 表記・
使い方ヘルプの文言。`president.html` は役割を持たないので対象外。

### 3.6 データ掃除

| 対象 | やること |
|---|---|
| 職人マスタの重複9件 | 統合。予定側の氏名は変えない（同名のため影響なし） |
| 人でない14件 | `有効=×` を立てる（**削除しない**。過去データが参照している） |
| `杉本凌（弟）` | 職人マスタに追加 |
| 文字化け1行 | `グロ?ライズ` → `グローライズ` に修正 |

⚠️ **実行前に `_local/backup_20260827/` へバックアップ**（アーカイブ作業と同じ手順）。

### ⛔ 絶対にやってはいけない順番

> **画面をGASより先に出してはいけない。**

新しい画面は `butai` を送るが、20列のままのGASはそれを保存しない。
利用者が部隊を選んで登録しても、その選択は**どこにも残らず消える**。
あとからGASを21列にしても本人が何を選んだかは判別できず**手で直すしかない**。
他の順番違いは「取り込みが止まって画面が遅くなる」だけで、原本は無傷なので復旧できる。
**復元不能なのはこの1つだけ。**

### ⚠️ 手順3の後、手順5の前に必ず確認すること

データ掃除はスプレッドシートだけを更新する。D1はCronが取り込むまで古いまま。
掃除の直後に画面を出すと、**過去の予定が一時的に部隊なしで表示される**。
