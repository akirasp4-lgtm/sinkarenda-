# 社長予定カレンダー 通信分離設計

最終更新: 2026-08-12

## 目的

社長専用カレンダーの読み込み・保存が、日報集計や帳票出力の長時間処理に巻き込まれて遅延・失敗する問題を解消する。朝6時・夜21時のLINE通知、既存データ、利用URL、認証方法は維持する。

## 本番確認結果

- LINEボットは Google Cloud VM `gr-bot` で稼働中。
- 朝6:00は当日、夜21:00は翌日の予定を社員ごとにLINE送信している。
- 社長本人の通知だけ、現在の予定管理GASへ `pres_list` を送信して社長予定を併記している。
- 本番VMの直近配信履歴で、社長予定が存在する日の通知本文に「社長予定」が含まれていることを確認した。
- 本番VMから現在の `pres_list` を実行し、178件・既存12列を正常取得した。応答時間は約3.3秒だった。
- 本番LINEボットの `handler.py` と `gas_client.py` はローカル版とファイル全体に差分がある。今回LINEボット側は変更しない。

## 原因

現在の `doPost(e)` は、リクエスト内容を判定する前に `LockService.getScriptLock()` を取得する。そのため、読み取り専用の `pres_list` と社長予定の追加・編集・削除も、日報集計や帳票出力と同じロックを共有する。

集計・出力がロックを長時間保持すると、社長予定の通信は最大10秒待機した後、「現在他の人が更新中です」で失敗する。また、社長予定の処理でも無関係な日報シートのヘッダー確認が毎回実行される。

## 採用設計

### 1. 社長予定アクションを先に判定する

`doPost(e)` の最初でJSON、合言葉、`action` を確認する。次の4アクションは、日報用の共通ロックと共通初期化へ入る前に専用ハンドラーへ渡す。

- `pres_list`
- `pres_add`
- `pres_update`
- `pres_delete`

### 2. 読み込みと書き込みを分ける

- `pres_list`: 読み取り専用なのでロックを取得しない。
- `pres_add` / `pres_update` / `pres_delete`: 同じGoogleユーザーからの同時書き込みを直列化する短いユーザーロックを取得する。
- 日報・集計・帳票出力は、現在のスクリプトロックをそのまま使う。

これにより、日報集計中でも社長予定を読み書きできる。異なるGoogleユーザーから書き込みが重なっても行番号がずれないよう、`pres_delete` は行自体を削除せず12列を空にし、`pres_list` はIDが空の行を返さない。これにより、削除と更新が競合しても無関係な予定を上書きしない。

### 3. 外部契約を変更しない

次の項目は変更しない。

- GASウェブアプリURLとデプロイID
- シート名 `社長予定`
- 12列の列名・順序
- `pres_list` のリクエスト・レスポンス形式
- `pres_add` / `pres_update` / `pres_delete` の形式
- 社長PIN、カレンダー合言葉、認証順序
- `president.html`
- LINEボット本番VM、朝6時・夜21時のスケジューラ、通知先、通知本文の組み立て方

## エラー処理

- JSONが不正な場合は、既存と同じJSON形式でエラーを返す。
- 合言葉が不正な場合は、既存の認証エラー形式を維持する。
- 社長予定の書き込みロックが取れない場合は、既存の「現在他の人が更新中です」と同等の再試行可能なエラーを返す。
- `pres_list` のシート取得・整形で例外が起きた場合は、既存の `status: error` 形式を維持する。

## テスト方針

Node.jsのテストハーネスでGAS依存を模擬し、実装前に次の失敗テストを作成する。

1. 日報用スクリプトロックが使用中でも `pres_list` が成功する。
2. `pres_list` が日報シートのヘッダー確認を呼ばない。
3. `pres_list` が既存12列を同じキーで返す。
4. 社長予定の追加が日報用スクリプトロックを使わず、社長予定用ロックを使う。
5. 日報系アクションは従来どおりスクリプトロックに守られる。
6. 削除が空行を残し、別の予定の行番号を変えない。
7. `pres_list` が削除済みの空行を返さない。
8. GAS全体のJavaScript構文チェックが通る。

## 本番反映と確認

1. ローカル自動テストと構文チェックを通す。
2. 既存デプロイIDの新バージョンとしてGASを更新し、URLを維持する。
3. 本番 `pres_list` で、既存12列と件数が維持されることを確認する。
4. 社長画面の更新応答時間を計測する。
5. 2099年の日付でテスト予定を1件追加し、取得確認後に同じIDを削除する。朝夕通知の対象日にはしない。
6. 本番VMから `pres_list` を呼び、LINEボットが同じ12列を読めることを確認する。LINE通知自体は送信しない。

## ロールバック

問題があれば、Apps Scriptの既存デプロイを直前のバージョンへ戻す。URLは変えないため、社長画面とLINEボット側の設定変更は不要。
