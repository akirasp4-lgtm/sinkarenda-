# 案A 設計書 — 保存を「押した瞬間」にする（楽観的表示＋裏送信）

**日付**: 2026-08-25
**対象**: 予定管理アプリ（`index.html` / `admin.html`）
**前提**: Cloudflare移行（読み取りのD1化）は同日11:25に本番切替済み

---

## 1. 目的と背景

保存に約4.4秒かかっており、社長打合せ（2026-08-24）でも
「遅い、そんなお客さんに出されへん」と速度が商品性の問題として挙がっている。

計測の内訳:

| | 時間 |
|---|---|
| GASの固定オーバーヘッド（69行の小さいシートを読むだけ） | 約1.0〜1.2秒 |
| 実際の書き込み作業（マスタ2種の読み直し＋2シートへの書き込み） | 約3秒 |

**GASの固定オーバーヘッド（約1秒）は構造上どうやっても消えない。**
したがって「実際に速くする」路線には1秒の壁がある。

一方、**送信するデータは送信ボタンを押した瞬間に全部そろっている**
（IDまでクライアント側で採番済み。`submitNippo` 参照）。
待っている4.4秒は「GASが受け取ったという返事」を待っているだけである。

→ **順番を入れ替えれば体感は0秒になる。** これが案A。

## 4. 設計

### 4.1 部品構成

```
[画面] submitNippo
   ├─→ addLocalRows(rows, {pending:true})   ← 即座に画面へ（0秒）
   ├─→ sendQueue.enqueue({id, rows, company})
   └─→ drainQueue()  ← 送信係を起こす（awaitしない）

[送信係 drainQueue] （画面側・fetchを持つ）
   ├─ sendQueue.nextDue(now) で1件取る
   ├─ 2回目以降なら → GASから最新を読み、IDが既にあれば送らず markSent
   ├─ fetch(GAS, action:'add')
   ├─ 成功 → sendQueue.markSent()  → 印を外す
   └─ 失敗 → sendQueue.markFailed() → バックオフして再挑戦

[send-queue.js] （純ロジック・DOMもfetchも触らない＝vitestでテスト可能）
```

**`send-queue.js` を別ファイルにする理由**: `sync-guard.js` と同じ。
`cf/test/` から読み込んで機械的にテストするため。画面に埋め込むとテストできない。

### 4.2 `send-queue.js` のインターフェース

```
createSendQueue({ storage, storageKey, maxItems, backoffMs, leaseMs, tabId })

  isStorageUsable()          → false なら呼び出し側は従来どおり同期送信に倒す（安全側）
  enqueue(item)              → {id, rows, company} を保存。上限超過なら false
  list()                     → 未送信一覧（表示用）
  count()
  nextDue(now)               → 今送るべき1件 or null（バックオフ・リース・世代を考慮）
  beginSend(id, now)         → 送信権を取る。取れたら {token, wasRetry}、取れなければ null
                               ★fetchの前に attempts を +1 して永続化する。
                                 wasRetry は +1 する前の attempts >= 1 か（§4.3）
  markSent(id, token)        → 箱から消す
  markFailed(id, token, e, now) → attempts++・次回時刻を設定
  markGaveUp(id)             → 自動再送を止める（手動のみに切替）
  retryNow(id)               → 手動再送（バックオフを無視）
```

保存形式（localStorage キー `yotei-pending-add-v1`）:

```
{ items: [ { id, rows, company, createdAt, attempts, nextAt,
             lastError, gaveUp, sendingBy, sendingAt } ] }
```

`id` は `submitNippo` が採番する先頭の `dayId` を使う。
**1回の登録が複数日にまたがると `dayId` は日ごとに複数あるが、
送信は1リクエスト＝1回の `setValues` で全か無かなので、
どれか1つのIDの存在を確認できれば全行の着地を判定できる。**

### 4.3 二重登録の防止（案①の詳細）

**「過去に一度でも送信を開始したことがある項目」のときだけ**、送信の直前に:

1. GASから最新データを取得（`?compact=1`。D1は最大5分古くなりうるので**使わない**）
2. そのキュー項目の `rows` に含まれるIDが1つでも見つかったら
   → **送らずに `markSent`**（＝前回は届いていた）
3. 見つからなければ送る

初回送信では確認しない（普段の登録に4.5秒を足さないため）。
**確認が走るのは失敗した後だけなので、日常の速度には一切影響しない。**

#### ★ `attempts` は「送信を開始した回数」であり、送信の**前**に永続化する

自己レビューで見つかった穴（2026-08-25）:

> 送信中にアプリ／タブが落ちると、「失敗した」と記録する前に死ぬ。
> `attempts` を失敗時に増やす設計だと、次に開いたとき **`attempts === 0`＝
> まだ一度も送っていない**と誤認し、存在確認を飛ばして送ってしまう。
> **サーバーには既に入っているので、これは二重登録になる。**
> §3で実測したエラー画面（実は書き込まれていた）と全く同じ形の事故が、
> 別経路で再発することになる。

したがって:

- `attempts` は **`beginSend` の中で、fetchを投げる前に +1 して localStorage へ書く**
- 存在確認をするかどうかは、**+1する前の値**で判定する（`attempts >= 1` なら再送）
- これにより「送信を開始した記録が残っているのに完了の記録が無い」項目は、
  次に拾われたとき必ず再送扱いになり、存在確認が働く
- **`attempts` の永続化に失敗した場合は、その項目を送らない**
  （記録が残せない以上、次回に再送扱いへ倒せないため。D3と同じ考え方で安全側）

### 4.4 送信を試みるタイミング

- 登録した直後
- **アプリを開いたとき**（起動時に箱を確認）
- 失敗からバックオフ経過後（5秒 → 15秒 → 45秒 → 2分 → 5分で頭打ち）
- **`window` の `online` イベント**（電波が戻ったとき）

### 4.5 表示

- 未送信の行は `isPending:true` を付けて `allNippos` に載せる
  （`isGhost` と同じ「表示専用フラグ」の前例に倣う。ただし `isGhost` と違い
  **集計からは除外しない**＝決定事項のとおり数える）
- 予定カードに時計マーク＋薄く表示
- 画面上部に「⏳ 未送信 N件」の帯。タップで一覧と「今すぐ送る」
- 送信できたら帯も印も黙って消える

## 5. 危険箇所と手当て（本設計の中心）

| # | 危険 | 手当て |
|---|---|---|
| D1 | **背景更新（`refreshInBackground`→`loadData`）が `allNippos` を丸ごと差し替えるため、未送信の行が画面から消える**（現行コードで実際にそうなる） | `loadData` 完了後に、箱に残っている未送信を**必ず載せ直す**。載せ直しは `rerenderAll` の前に行う |
| D2 | **複数タブ／複数端末が同時に同じ項目を送り二重になる** | (a) 初回送信は**登録したタブだけ**が行う（メモリ上の所有権）。他タブは `leaseMs`（30秒）経過後にしか拾わない＝そのときは必ず「2回目以降」になり §4.3 の存在確認が効く。(b) `beginSend` は `sendingBy`/`sendingAt` を書いて読み直し、自分のtabIdが残っていれば所有とみなす |
| D3 | **localStorage が使えない**（iOS プライベートモード・quota超過） | `isStorageUsable()` が false なら**楽観化を一切行わず、従来どおり同期送信して待たせる**。無言で未送信を失うことを絶対にしない |
| D4 | 箱が溜まりすぎる | `maxItems`（50件）超過時は `enqueue` が false を返し、呼び出し側は従来どおり同期送信に倒す |
| D5 | **何度送ってもダメ**（データ不正など、再送では直らない失敗） | `attempts` が10回を超えたら `gaveUp` にして自動再送を止め、**消えない赤い警告＋手動再送ボタン**を出す。**勝手に捨てない** |
| D6 | 会社を切り替えたとき未送信が混ざる | 項目に `company` を持たせ、表示中の会社の行だけカレンダーに出す。帯の件数は全社分を出す（見落とし防止） |
| D9 | **送信中にアプリ／タブが落ち、失敗の記録が残らない** | `attempts` を**送信の前**に永続化する（§4.3の★）。落ちた項目は次に必ず再送扱いになり存在確認が働く |
| D7 | **送信成功したのに `markSent` の localStorage 書き込みが失敗し、再送されてしまう** | §4.3 の存在確認が最終防衛線として機能する（2回目以降は必ず確認するため二重にならない）。加えて6回目レビュー修正2と同じく、書き込み失敗時はキーを消してメモリへフォールバック |
| D8 | 未送信の行に `jobNo`（工番）が無い | 現行の `addLocalRows` も `jobNo:''` で載せている＝**既存の挙動と同じ**。背景更新でサーバー採番の値に置き換わる。今回の変更で悪化しない |

## 6. テスト方針

`send-queue.js` は純ロジックなので `cf/test/send-queue.test.js` から vitest で検証する
（`sync-guard.js` と同じやり方。現在153件が通っている）。

必ず含めるケース:

1. **「1回目が届いていたのに返事が消えた」→ 再送前の存在確認で二重にならない**（§3の実測を再現）
1b. **送信開始の直後に落ちた（失敗の記録が無い）項目も、次は再送扱いになる**（D9の再現）
1c. `attempts` の永続化に失敗したら、その項目を送らない
2. 初回送信では存在確認をしない（余計な4.5秒を足さない）
3. バックオフが規定どおり伸び、頭打ちする
4. **2つのタブが同時に `beginSend` しても、片方しか送信権を取れない**
5. リース切れの項目は他タブが拾える（送信中のまま永久に固まらない）
6. localStorage が使えないとき `isStorageUsable()` が false を返す
7. 上限超過時に `enqueue` が false を返す
8. `gaveUp` の項目は `nextDue` に出てこない／`retryNow` では送れる
9. **既存153件が壊れていない**

画面側（`index.html` / `admin.html`）は構文チェック＋実機確認。
